### Current Behavior

Two semantically equivalent filters select the same 1,985 entities, but the AND-TRUE identity filter representation is 2.706x slower in client end-to-end ANN latency.

Equivalent-filter property: `F is equivalent to F AND TRUE AND ... AND TRUE`.

| Measurement | Original filter | Equivalent filter |
|---|---:|---:|
| Eligible entities | 1,985 | 1,985 |
| ANN p50 | 7.5698 ms | 20.4838 ms |
| Exact/FLAT p50 | 36.2075 ms | 46.4984 ms |
| Recall@10 | 1.0000 | 1.0000 |

- ANN symmetric latency ratio: 2.706x
- Equivalent/original latency ratio: 2.706x
- Exact/FLAT symmetric latency ratio: 1.284x
- Eligible-set equality: `True`
- Exact Top-K equality: `True`

The public Milvus search response does not expose request-scoped visited-node, distance-computation, or candidate counters. This report therefore describes a reproducible equivalent-filter search latency anomaly, not a confirmed ANN optimization bug.

### Expected Behavior

Semantically equivalent filters should select the same entities and should not cause an unexpectedly large search-latency difference when the vector query, collection, index, `top_k`, HNSW `ef`, and consistency level are unchanged.

### Anything else?

This issue may appear similar to [#54043 ](https://github.com/milvus-io/milvus/issues/54043), as both report search latency differences between semantically equivalent filters.

However, the two issues involve different filter equivalence rules. This issue specifically focuses on the **AND-TRUE identity law** (`F AND TRUE ≡ F`), where redundant predicates that are always true for the dataset are added to the original filter.

Although the observed symptoms are similar, the underlying equivalence transformations are different and may exercise different filter processing or optimization paths. Therefore, we report this case separately to highlight a distinct equivalence rule that can trigger a reproducible performance anomaly.
